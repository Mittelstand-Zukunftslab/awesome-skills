# How It Works — @shadcn/lint

The linter reads your components, theme, and variants to check how you use
them. It analyzes source code without running your app.

---

## Component discovery

### From components.json

`components.json` points to the UI directory. The linter reads exported
components and resolves imports through:

- `@/` aliases
- tsconfig `paths`
- Package `imports`
- Workspace package `exports`

It follows re-exports and renamed imports back to the defining file:

```tsx
// components/widgets.ts
export { Button as Action } from "./ui/button"
```

```tsx
import { Action } from "@/components/widgets"

// no-restyle reports a color override on Button (the resolved name).
<Action className="bg-primary">Save</Action>
```

### Default export

A default export counts under the component's own name, including wrappers
like `export default memo(Button)` or `forwardRef`.

### Without components.json

The linter uses the nearest `package.json` and looks in `components/ui` or
`src/components/ui`. For another location, set `settings.shadcn.ui`:

```js
settings: {
  shadcn: {
    ui: "@/ds",
  },
}
```

### Name matching fallback

A component from another package does not become a design-system component
just because it has the same name. Name matching is a fallback only when an
import cannot be resolved. An unresolved UI alias produces a warning with
the configuration to fix.

## Theme tokens

The theme CSS comes from `components.json`. It follows the theme's
`@import`s and reads `--color-*` declarations in `@theme`:

```css
@theme inline {
  --color-primary: var(--primary);
  --color-brand: var(--brand);
}
```

- `bg-brand` — ✅ allowed, declared token.
- `bg-zinc-100` — ❌ reported, raw palette color.
- `bg-highlight` — ❌ reported, undeclared token.

### Utility-specific namespaces

Tailwind reads a color from the utility's own namespace before `--color-*`:

| Declaration | Declares | Does NOT declare |
|-------------|----------|------------------|
| `--background-color-surface` | `bg-surface` | `text-surface` |
| `--text-color-ink` | `text-ink` | `bg-ink` |
| `--border-color-edge` | `border-edge` | `text-edge` |

### Suggestions

The linter resolves CSS variables from `:root`, skips `.dark` blocks, and
compares colors in OKLab. It also reads the radius and text scales,
including `calc()`. For example, `rounded-[10px]` can suggest `rounded-lg`
when that token is 10px.

### Without components.json

The linter finds a stylesheet that imports Tailwind. If several qualify,
it picks the one with the most color tokens, then the one nearest the
project root.

## Tailwind class validation

`no-unknown-classes` asks your installed Tailwind v4 whether each class
generates CSS. It loads your theme with its imports, custom utilities,
variants, plugins, and config.

- Runs in a **worker thread** (async loader).
- Answers are **cached per theme**.
- If Tailwind can't load, the rule warns and uses a grammar fallback.

Custom utilities (`@utility`) and plain class selectors in the theme's
import graph are recognized. Classes generated by Tailwind plugins (e.g.,
`prose` from the typography plugin) also pass.

---

## Variant reading

`no-restyle` suggests variants found in the component file. It reads:

- `cva` and `tv` definitions.
- Props typed as string unions: `variant?: "default" | "destructive"`.
- Props typed as `keyof typeof` a lookup object.

Props resolve through intersections, unions, and same-file type aliases.
When props are a union of shapes (anchor or button), the listed variants
are the ones every member accepts.
